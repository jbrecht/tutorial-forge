## Repo context
tutorial-forge is a pnpm TypeScript ESM monorepo that renders narrated tutorial videos: Playwright drives the app under test while a TTS provider synthesizes the narration, and a single ffmpeg pass stitches the result. Its users are tutorial authors; the paths every author crosses are `render` and the record phase.
- `packages/core` (published as `tutorial-forge`): the engine. Three phases, tts → record → post, in `src/pipeline/`. Pure, testable helpers live in `src/post/` (ffmpeg, zoom, retime, gif, subtitles, captions, cards, chapters), `src/browser/timing.ts` and `src/spec.ts`; browser-side instrumentation (callouts, cursor, console) in `src/browser/`; the TTS providers and their content-hash cache in `src/tts/`. The public API is only what `src/index.ts` re-exports.
- `packages/cli` (published as `tutorial-forge-cli`): commander-based `render / list / doctor / clean` over the core, plus `preview`, in `src/main.ts` plus one file per command.
- `packages/example-app`: the app under test ("Lumen Events") plus the e2e render harness, `test/e2e.ts`. Not published.

## Stack cautions
- The fiddly correctness here lives in ffmpeg filtergraph strings (escaping, stream labels, `enable='between(t,...)'`, palettegen/paletteuse, signalstats) and Playwright timing. Before flagging an ffmpeg arg array or filter string as wrong, check it against the golden tests in `packages/core/test/` (`ffmpeg-args.test.ts`, `zoom.test.ts`, `retime.test.ts`, `gif.test.ts`, `captions.test.ts`, `cards.test.ts`, `chapters.test.ts`) and the pure builder it came from; if behavior changed, a golden test should have changed too. Never assert that a flag or filter doesn't exist from memory.
- Playwright's `recordVideo.size` larger than the viewport pads the frame; it never scales. Recording runs at viewport size with `deviceScaleFactor: 2` (`pipeline/record.ts`), so `page.screenshot()` output is 2× the CSS viewport on every machine: that's emulation, not a display property. "Record at 2× and downscale in post" is impossible with `recordVideo`; the screencast recorder exists for that.
- Calibration flash (`post/ffmpeg.ts`): `detectFlashOffsetMs` returns `number | null`. `0` means the flash is on the first frame (VP8 coalesces the identical pre-flash frames); `null` is the miss. Assert `!== null`, never `> 0`. CI often decodes the webm in limited range (16–235), so the chroma test uses the single `FLASH_CHROMA_MIN` for both channels, and the scan is one `signalstats,metadata=print:file=-` filter: chaining two metadata filters duplicates frame headers.
- `page.screenshot({ style })` injects CSS into the live page. Inside a recorded hold, anything beyond hiding a caret shows as a stutter and can destroy an in-flight CSS transition.

## What to check
**Timing math** (`stepHoldUntilMs`, `computeCues`, `computeIdleSegments`, `computeZoomWindows`, the retime time-maps): ms vs s, off-by-one, the two regimes (action outlasts narration vs narration outlasts a near-instant action) and the silent step (`audioDurationMs === 0`). They feed each other; a change to one usually needs the others.
**The sync path.** Anything that records or trims keeps the calibration flash detectable (it sets `videoClockOffsetMs`) and trimmed out of the final video. Narration clips are laid at measured offsets; nothing may risk drift.
**ffmpeg builders.** Stream-label wiring; filter order when features compose (zoom + idle-speedup + captions + cards + chapters + gif on one render); graceful fallback when a filter is missing (`ffmpegHasFilter`). Everything must work on every ffmpeg build: no required encoder, hwaccel or libass.
**Processes and cleanup.** Work dirs removed unless `--keep-work`/`--debug`; no orphaned servers or browser contexts on the error path. Under `--render-concurrency` (`mapLimit`), a failure stops scheduling and awaits in-flight jobs before rejecting; languages are de-duplicated; shared caches write through unique per-call temp paths (the TTS cache once raced on same-key synthesis).
**Side artifacts never fail the render.** Stills, contact sheet, gif, chapters, cards: anything that can throw while building one (a filename-collision check, say) sits inside the warn-and-continue guard in `pipeline/render.ts`, not in an argument expression that calls it, and a blocked side-artifact path still yields the MP4. Work dirs (`.forge/<id>/`) are reused, so a consumer of record's per-step frames gates on manifest membership (`recorded`), not on a file existing, and prunes its generated output from the previous `index.json` keyed by filename, never by id or a name pattern (a regex once deleted an author's own files).
**Record and preview share one step lifecycle** (`pipeline/step-hooks.ts`: `createStepContext`, `safeTeardown` and `runStepTeardowns` in LIFO order, `anchorFocus`, `waitForSettle`). New lifecycle behavior goes there and is called from both phases; the teardown order is asserted only in e2e against record, so divergence is silent. One difference is deliberate: preview replays prior steps on the raw page and instruments only the target step. Both run the full teardown chain on every exit path, including a step failure (`runTeardownChain`: step thunks → tutorial → adapter), and so does the doctor setup probe.
**i18n.** `localizeTutorial` keeps step ids stable across languages so timing, captions, stills and caches line up; translation files use the reserved keys `__objectives__` and `__summary__`.
**Public API and semver.** What `src/index.ts` in `packages/core` re-exports, and the CLI's commands and flags, are the contract; the two packages ship in lockstep, so a change there needs the matching bump in both `package.json` files (the publish-reviewer checks the packed surface).
**Tests.** New pure logic (builders, timing, cue and subtitle computation, gif and stills windows, i18n, cache keys, CLI resolvers) gets a vitest test in `packages/core/test/` or `packages/cli/test/`; behavior changes update golden expectations rather than weakening assertions. A render-pipeline change is exercised by `packages/example-app/test/e2e.ts` where feasible, and a behavior verified live against the example app is folded into it as a durable assertion rather than left as a throwaway script. A test proves a fix only if it runs the changed line: the stills parity check once measured a path the change didn't touch.
**Quality.** ESM hygiene: `.js` extensions on relative imports (`"type": "module"` + NodeNext), no CJS-isms. Cross-platform paths via `node:path`, no hardcoded `/tmp`. Reuse the helpers in `src/util/` (`ensureDir`, `removeDir`, `exists`, `mapLimit`, `sha256`, `logger`) and `src/post/`; step-range parsing (`a..b`, `--gif-steps`) already lives in `post/gif.ts` (`resolveGifWindow`), so a new range option reuses it rather than adding a second parser. A helper exported only for tests is dead code.
No UI here: the example app is a fixture, so skip the accessibility audit unless the diff changes `packages/example-app/public` or `packages/example-app/src`.

## Defaults
- Base branch: `origin/main`.
- Checks: `pnpm -r typecheck`, and `pnpm --filter tutorial-forge test <name>` (or `--filter tutorial-forge-cli`) for the test files covering the changed code. Don't run `pnpm e2e`: it takes two to three minutes with real browsers and ffmpeg; say when the diff needs it.
- Skip: `docs/assets/`.
